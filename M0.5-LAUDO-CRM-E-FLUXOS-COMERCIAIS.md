## ACHADOS CRÍTICOS

### Achado #1: Desconexão entre Lead State e Email Cadence
**Severidade:** CRÍTICA  
**Problema:** 
- `core/lead_state.py:CLOSED_STATUSES` = {sem_interesse, numero_errado, encerrado, stop, failed}
- `email_cadence/engine.py:STOP_STATUSES` = {clicked_warm, replied, won, ..., shared_phone_blocked}
- **Impacto:** Email pode continuar sendo enviado para leads que estão "sem_interesse" no estado do lead

**Evidência:**
```python
# core/lead_state.py:14
CLOSED_STATUSES = {"sem_interesse", "numero_errado", "encerrado", "stop", "failed"}

# email_cadence/engine.py:49-63
STOP_STATUSES = {
    "clicked_warm", "replied", "won", "lost", "opt_out",
    "wrong_contact", "done", "stopped", "warm",
    "meeting_booked", "calendly_booked",
    "shared_email_blocked", "shared_phone_blocked",
}
```

**Recomendação:** Sincronizar estas duas estruturas

### Achado #2: Cadência Intervals Replicadas em 3 Locais
**Severidade:** CRÍTICA  
**Problema:** Mesma regra (CAD_1-6 intervals) definida em:
1. `config/cadence_config.json` (JSON)
2. `core/cadence_manager.py` (DEFAULT_CADENCE)
3. `config/config_manager.py` (init cadence)

**Impacto:** Mudança em um local não sincroniza com os outros. Sistema pode usar valores inconsistentes dependendo de qual fonte é carregada primeiro.

**Evidência:** Todos os 3 locais têm `[0, 3600, 86400, 172800, 259200, 432000]`

**Recomendação:** Fonte única de verdade - preferência: JSON config com fallback em código

### Achado #3: Phone Validation em 3 Implementações
**Severidade:** ALTA  
**Problema:** Validação de telefone implementada em:
1. `crm/crm_orchestrator.py` (_normalizar_telefone_br)
2. `services/whatsapp_service.py` (normalize_phone)
3. `core/lead_state.py` (normalize_phone)

**Impacto:** Bug em um local não será fixado em todos. Regras podem divergir.

**Recomendação:** Centralizar em `utils/phone_utils.py`

### Achado #4: Pipeline ID Hardcoded
**Severidade:** MÉDIA  
**Problema:** 
- PIPELINE_ID = 2 em crm_orchestrator.py:800
- PIPELINE_ID = 2 em pipeline2_holiday_hygiene.py:1

**Impacto:** Mudança de pipeline requer edit em múltiplos arquivos

**Recomendação:** Mover para `config/system_config.json`

### Achado #5: Stages Fallback Order Hardcoded
**Severidade:** MÉDIA  
**Problema:** 
```python
STAGE_FALLBACK_ORDER = [
    "Lead novo", "Contato iniciado", "Conversando", 
    "Reunião marcada", "Proposta", "Ganho", "Perdido"
]
```

**Impacto:** Mudança de stages requer edit no código Python

**Recomendação:** Mover para `config/system_config.json` ou buscar do Pipedrive API

### Achado #6: Priority Queue Splitting Não Documentado
**Severidade:** MÉDIA  
**Problema:** 
```python
priority_super: List[Dict[str, Any]] = []
filtered_high: List[Dict[str, Any]] = []
# Splitting logic não tem critério claro documentado
ordered = priority_super + filtered_high
```

**Impacto:** Difícil entender por que alguns leads são priorizados sobre outros

**Recomendação:** Documentar critério de split em código e contrato

### Achado #7: Email URLs Hardcoded
**Severidade:** BAIXA  
**Problema:** 
```python
CALENDLY_URL = os.getenv("CALENDLY_URL", "https://calendly.com/ana-manddigital/30min")
FORM_URL = os.getenv("PREFORM_URL", "https://docs.google.com/forms/...")
```

**Impacto:** URL específica de "ana-manddigital" hardcoded, não é genérica

**Recomendação:** Usar env vars apenas, remover hardcoded

### Achado #8: Gemini Model Hardcoded
**Severidade:** BAIXA  
**Problema:** 
```python
gemini_model: str = "gemini-1.5-flash"
```

**Impacto:** Upgrade de modelo requer edit de código

**Recomendação:** Mover para `config/system_config.json`

### Achado #9: Lead Cards vs Lead State Duplicate Storage
**Severidade:** MÉDIA  
**Problema:** Dois sistemas de armazenamento:
- `core/lead_state.py` - Estado booleano de lead
- `core/lead_cards.py` - Card com histórico de atividades

**Impacto:** Potencial de inconsistência entre dois sistemas

**Recomendação:** Consolidar ou claramente separar responsabilidades

### Achado #10: Activity Logging em 3 Sistemas
**Severidade:** MÉDIA  
**Problema:** Atividades registradas em:
1. `crm/activity_registry.py` - Timeline
2. `core/lead_cards.py` - Card history
3. `core/event_logger.py` - Event log
4. `core/db_manager.py` - Dispatch logs

**Impacto:** Difícil rastrear linha histórica única de um lead

**Recomendação:** Consolidar em um sistema único de auditoria
